# V2.2.2 Representative Clean-Lap Pace

## A. Objective

V2.2.2 adds RaceBrain's first numerical V2 model: a deterministic, interpretable estimate of a competitor's recent representative clean-lap time at historical cutoff `T`. It is a baseline for later models, not a claim about pure car or driver performance.

## B. Exact pace semantics

An available result is the median observed lap time, in `s/lap`, among the clean observations selected from that competitor's configured recent lap-number window. Lower values are faster. The value means only “representative recent observed clean-lap time”; it is not intrinsic, clean-air, fuel-corrected or tyre-corrected pace.

## C. Why median

The standard-library median is deterministic, transparent, robust to an isolated unusual lap, distribution-free and dependency-free. It establishes a simple baseline against which later estimators can be evaluated.

## D. Input boundary

The pure model service in `app.models_v2.representative_pace` accepts only immutable, provider-independent `PaceEstimationContext` plus typed `PaceModelConfig`. It cannot receive an OpenF1 client, DTO, provider key, raw response or V1 simulation object, and has no fetch path. It provides independent competitor and full-field entry points.

## E. Trailing window semantics

For a competitor whose latest admitted observation is lap `L`, the candidate interval is `[max(1, L - lookback_laps + 1), L]`. Candidates are admitted observations whose lap numbers fall inside that interval—not the last N observations. A missing canonical lap does not pull an older lap into the window, and the window is never expanded to chase the minimum sample count.

The initial `lookback_laps=8` and `minimum_clean_laps=3` are explicit baseline design parameters, not Formula 1 physical constants.

## F. Hard exclusion policy

Every factual `LapExclusionReason` attached by V2.2.1 is disqualifying: lap one, pit out, pit-lane affected, safety car, VSC, red flag, global yellow and insufficient context. These are not optional switches. Multiple reasons on one observation exclude one lap while each encountered reason remains visible in the audit.

## G. Soft warning policy

Only warnings named in configuration disqualify a lap. The baseline excludes `WEATHER_TRANSITION`. It does not automatically exclude `TRAFFIC_SUSPECTED` or `EXTREME_OUTLIER`, and V2.2.2 adds neither classifier. A configured warning plus a hard reason still excludes one observation.

## H. Candidate, included and excluded definitions

`candidate_laps` counts admitted observations in the configured interval. `included_laps` counts candidates used in the median. `excluded_laps` counts candidates rejected by hard reasons or configured warnings; observations outside the interval are not exclusions. The invariant is `candidate = included + excluded`. `PaceSelectionAudit` carries canonically ordered typed counts per encountered hard reason and per configured warning that caused rejection.

## I. Insufficient evidence

Fewer than three selected clean laps yields no `PaceEstimate`. The per-competitor fit remains present with accurate diagnostics, `INSUFFICIENT` diagnostic quality, a deterministic warning and the typed reason `INSUFFICIENT_RECENT_CLEAN_LAPS`. This also covers canonical competitors with zero modelling observations. No older laps, excluded laps, other competitors or field average are substituted.

## J. Evidence window

An available estimate's `sample_count` equals `included_laps`. Its evidence window contains the minimum and maximum included lap numbers and the earliest and latest included completion timestamps. Excluded candidates do not appear as evidence.

## K. Residual diagnostics

For each included observation, residual is `lap_time_s - median_pace_s`. Diagnostics report the median residual and `median(abs(residual))`. The latter is descriptive median absolute residual in seconds; it is not sigma or an uncertainty interval.

## L. DataQuality semantics

`DataQuality` is not a selection flag. In particular, OpenF1 observations whose completion time is approximated from `date_start + lap_duration` remain eligible. Available estimate quality contains only timing-evidence limitations relevant to this calculation, uses `completeness=None`, and does not inherit missing gap or tyre fields that the estimator does not consume. Current live OpenF1 estimates are consequently `DEGRADED`. Insufficient fits are `INSUFFICIENT`. Quality is neither confidence nor probability.

## M. Provenance

Available estimates and diagnostics carry deterministic model-level provenance stating that canonical bounded context was selected, factual/configured exclusions were applied, and standard-library median aggregation was used. The entry records model version and config hash without fabricating source timestamps or duplicating provider metadata. Existing estimate and diagnostic cutoff validators prohibit future-observed provenance.

## N. Model config, version and hash

The approved baseline is:

- model `representative-clean-pace`, version `0.1.0`
- trailing lookback `8` lap numbers
- minimum `3` clean laps
- excluded warnings: `WEATHER_TRANSITION`
- no random seed

`PaceModelConfig.version()` hashes the complete canonical JSON configuration with SHA-256. Changing lookback, minimum sample count, warning policy or model version changes model/config identity. Every field result, estimate and diagnostics object carries the same version generated by its configuration. The approved live hash is `sha256:ad8ba93d200ae7239d94a9ae471cbc8faaed3f2d3af3935c4e1723358fd8c7f0`.

## O. No-hindsight invariant

V2.2.1 bounds every observation to context cutoff `T`; V2.2.2 is a pure function of that context and config. No later-completed observation can influence selection, exclusions, value, diagnostics, quality or provenance. Synthetic provider→context→estimate contamination tests produce exactly equal contexts and full pace outputs at the same cutoff. Advancing the cutoff may legitimately roll the window and change the estimate without mutating the earlier result.

## S. Known limitations

Each estimate deterministically discloses that it does not separately identify or correct fuel burn, tyre-age degradation, compound performance, track evolution, traffic/dirty air, driver management, energy deployment, or local weather beyond configured exclusions. The window may span tyre states. Approximate provider lap-completion timestamps remain visible. A local trailing window reduces temporal breadth but does not resolve these identifiability limits.

## T. Explicit non-goals

V2.2.2 does not implement arithmetic-mean/regression pace, fuel/tyre/track/traffic correction, clean-air or intrinsic performance, relative pace, simulation, strategy advice, probability, fabricated confidence, uncertainty, tyre degradation, a modelling API, frontend columns, V2.3 or V2.4 work.

Available point estimates therefore use `uncertainty=None` and `confidence=UNKNOWN`.

## U. Proposed V2.2.3 boundary

V2.2.3 may add an independently reviewed tyre-age pace-slope estimator in `s/lap/lap` only when bounded context supplies adequate compound and tyre-age evidence with a positive age span. It should consume the same canonical provider-independent context, keep degradation separate from this representative-pace result, expose fit/exclusion/identifiability diagnostics, and preserve all no-hindsight and versioning guarantees. No such estimator is implemented here.
